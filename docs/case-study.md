# 案例：制药企业物料/成品仓质量合规助手（GMP）

> 这是基于公开 GMP 通用要求设计的**合成场景**，用于验证 RAG/Agent 在受监管业务里的落地方式；不是某家客户的真实系统，也不涉及任何真实业务数据。

## 一句话

把"查批记录 / 查偏差 / 查储存条件 / 判断能否放行"从**人来回切 ERP、LIMS、SOP 文档**，变成一句问清楚、有依据、可审批、可审计。

## 用户与痛点

**用户**：制药企业仓库管理员、QA、质量受权人（QP）相关的质量人员。

**典型问题**：

- 这批成品/物料现在是什么状态？批记录完整吗？有没有未关闭偏差？
- 该放哪个库区？储存条件是什么？当前温控是否合规？
- 这批能不能放行？依据是哪条 SOP/GMP 要求？
- 放行/隔离这类写操作，谁批的、什么时候批的、能不能追溯？

**现状痛点**：

- 批记录、偏差、放行状态在 ERP/MES/LIMS；规范在 SOP/GMP 文档——**两套系统来回切**
- 判断依赖个人经验，新人容易漏（尤其批记录完整性、偏差关闭状态）
- 审计要能说清"当时依据什么、看了哪些数据、谁批的"

## 三个用户旅程

### 1. 批次状态核对（读）

> "QS-2024-9527 的库区、批记录、偏差和放行状态？"

助手：调用外部仓储/质量系统（MCP mock）→ 返回库区、储存条件、QA 状态、批记录完整性、未关闭偏差、有效期、结存 → 按契约组织答案。

### 2. 成品放行（写，必须人工审批）

> "把 QS-2024-6001 放行。"

助手：识别为写操作 → **暂停等审批**（`awaiting_approval`）→ 批准后执行 `release_batch` → 状态持久化；不满足条件时逐条说明：

- 批记录不完整 → 不放行
- 存在未关闭偏差 → 不放行
- 状态不是"待放行" → 不放行

拒绝/超时一律不执行（fail-closed），决策写审计；执行台账保证重放不重复放行。

### 3. 多步合规核对（Plan-and-Execute）

> "查 QS-2024-9527 的库区状态，再查 SOP 里冷藏库的储存要求，判断是否合规。"

助手：生成计划（查系统 → 查 SOP → 对比）→ 人工审批计划（可改参数）→ 逐步执行 → 合成带引用的结论。

## 方案结构

```
用户问题
  → 意图路由（rag / tool / chat）
  → RAG：结构感知父子块 + 向量/BM25 + RRF + Rerank，答案带 [n] 引用
  → MCP：GMP 仓储 mock（批记录/偏差/QA 状态/放行）
  → 写操作：人工审批（interrupt + checkpointer 续跑，超时 fail-closed）
  → 执行台账：危险工具按 tool_call_id 落账，重放不重复
  → 多步任务：Plan-and-Execute（计划审批 → 按步执行 → 合成）
  → trace / 评测 / 成本预算
```

## 关键取舍

| 决策 | 为什么 |
|---|---|
| 结构感知父子块 | 子块检索准，父块补上下文；表格/标题不能被拦腰切断 |
| 答案必须带引用、拒答不带引用 | 受监管场景要能对回原文；没依据就明说，不能编 |
| 外部工具人工审批 | 查询/放行是跨系统动作，必须可控、可审计 |
| 执行台账 at-most-once | 宁可漏执行让人复核，也不重复放行/重复副作用 |
| 计划执行不自动 replan | 多步任务先批计划，失败不自我循环，避免成本失控 |
| 用 MCP mock 而不是重做 WMS | 演示重点是 agent 接外部系统 + 治理，不是 CRUD 产品 |
| 合成数据 | 不涉及真实客户/前公司材料；规则按公开 GMP 通用要求设计 |

## 失败路径（都测过）

- 外部工具超时 → 有界超时，报告失败，不伪造数据
- 审批拒绝 / 超时 → 不执行，模型如实说明，写审计
- 批记录不完整 / 偏差未关闭 → 放行被拒
- 检索无命中 → 拒答，不切模型自答
- 台账不可用 → fail-closed，危险工具不执行
- 结果落盘失败 → 降级为截断，不 500

## 可验证的数据

- 检索：61 题固定集，rerank 关→开 recall@1 0.59→1.0、MRR 0.772→1.0
- 生成：12 正 + 8 负，正确率 91.7%、引用正确率 100%、8/8 干净拒答
- Agent：8 任务，路由/完成率/步数/token
- 路由：14 题固定集 14/14（规则分类，零 LLM 花费）
- 计划执行：5 个多步任务 5/5，平均 1.8 步 / 2877 token / 16.1s
- 工程：121 个测试，含故障注入、跨租户隔离、审批/重放/台账

## 演示方式

```bash
make run       # 本地起服务（嵌入式 Chroma + SQLite）
# 查询
POST /api/v1/agent/chat  {"question": "批号 QS-2024-9527 的库区、批记录和放行状态"}
# 放行（会返回 awaiting_approval）
POST /api/v1/agent/chat  {"question": "请把批号 QS-2024-6001 放行"}
POST /api/v1/agent/approve {"conversation_id": "...", "decisions": [{"tool_call_id": "...", "type": "approve"}]}
```

放行结果写入 `data/wms_mock.json`；删除该文件即恢复初始数据。

## 边界（如实说）

- 合成数据、合成 SOP；按公开 GMP 通用要求设计，不是客户系统
- 只做 GMP 物料/成品仓语境，**不是 GSP 流通**（收货验收/随货同行单那套不在这里）
- 没有真实 MES/LIMS/ERP 对接；MCP mock 只模拟查询与放行
- 没有质量受权人的电子签名/合规签批
- 没有平台级多人会签/审批中心

## 30 秒讲法

> 我选的是制药企业 GMP 场景：物料/成品仓，核心是批记录、偏差、放行。痛点很具体——数据在系统里、规范在文档里，人要来回核对，还要留痕。我用 MCP mock 接外部系统、RAG 查规范、人工审批卡写操作、执行台账防重复、计划执行做多步核对；答案带引用、拒答不带引用。演示数据是合成的，但失败路径和评测都是真的。
